## 1. 背景与价值

用户是使用 fdecode 的软件工程师：有技术背景，但不是 fdecode / Pi 的开发者。当前 agent 的行为对他们是**经验性**的——能观察结果（流式输出、工具卡片、费用），观察不到机制：模型实际看到什么、会话被装配了什么、哪条策略在生效、哪次工具调用被动过。出异常时只能靠经验猜测，或去读源码。

同类 coding agent 工具普遍不提供这个层次的可视化（邻接先例存在：个别工具有 token 构成命令或会话日志可读，但没有把"生效配置合并 + 扩展装配注册 + 治理审计 + 上下文解剖"作为一等公民产品面）。差异化主张是**深度与整合**，不是"首创可视化"。

本需求的结构性优势：transcript 是追加式唯一事实源，"Model-visible ⟺ logged"不变量意味着**解释 agent 行为所需的全部数据已被 substrate 记录**（system prompt 增量、工具集变更、context_edit、压缩切点、重试）。竞品要做此事需事后补遥测或逆向闭源 substrate；我们只需要把已有事实流翻译成视图。教程线 29 篇 `docs/explains/` 笔记即是本需求的**内容地图**——"模型到底看到什么""为什么被压缩""为什么被拦"正是要在运行期回答的问题。本需求的本质：把教程线的死知识运行期化、上下文化。

价值：从"黑盒 + 经验猜测"到"白盒 + 可检验因果"——每个行为异常都能追溯到一个可检查的原因。

## 4. 使用场景

### 场景 1：上下文异常排查

- 触发条件：多轮后 agent "忘了"早先约定，或行为突然变化，用户想知道为什么。
- 参与者：软件工程师（用户）、fdecode 观测视图。
- 期望结果：打开上下文解剖视图，看到当前上下文构成（system prompt 各分节、工具、消息历史、压缩摘要）与各部分占用；结合机制时间线确认"某次压缩切掉了哪些内容"，定位原因，不猜。

### 场景 2：装配确认

- 触发条件：切换工作区、新成员入职、或"换个目录 behave 不一样"。
- 参与者：用户、观测视图。
- 期望结果：装配视图展示该会话的生效配置（三源合并、逐键优先级、来源文件路径）与实际加载的扩展/工具/MCP；用户能指出"这个行为来自这个扩展，配置来自这个文件"。

### 场景 3：治理追溯

- 触发条件：一次工具调用的参数或结果与预期不符，怀疑被钩子拦截或改写。
- 参与者：用户、观测视图（治理审计）。
- 期望结果：该次 tool_call 的拦截/改写/放行记录可查，能看到是哪个扩展的哪个钩子做了什么。

### 场景 4：机制理解

- 触发条件：会话中途出现压缩、自动重试、上下文溢出恢复，用户想知道发生了什么。
- 参与者：用户、观测视图（机制时间线）。
- 期望结果：会话内时间线展示这些机制事件的时序与细节（压缩触发条件与切点、重试原因、恢复动作），与对话流可对照。

## 6. 功能性需求

- **FR-1 上下文解剖**：新增只读命令返回当前请求上下文的构成——system prompt 各分节（基础 prompt、AGENTS.md、skills、扩展注入）、工具声明、消息历史、压缩摘要、context_edit——及各部分占用（token 计数精确或近似，由 spike 定并标注口径）；fdecode 以分解视图呈现。
- **FR-2 生效配置视图**：读取三处配置源并展示逐键合并结果：每个键的生效值、优先级、来源文件路径；纯文件读取，无核心改动。
- **FR-3 运行期装配注册表**：新增只读命令返回当前会话实际加载的扩展及其注册项（工具、钩子、命令、渲染器）、MCP 连接状态；按会话展示。
- **FR-4 机制时间线**：fdecode 将压缩（触发、切点、摘要范围）、溢出恢复、自动重试、队列转换等机制事件呈现为会话内时间线，与对话流可对照。
- **FR-5 治理审计视图**：tool_call 钩子的拦截/改写/放行动作可留痕、可查看（留痕机制由 spike 定：核心统一留痕或扩展自报）。
- **FR-6 只读契约**：全部新增命令只读、无副作用，遵循既有 RPC 协议（JSONL、id 关联、response 包络）；不修改既有命令语义；以一次 vision 方向性决策覆盖整族，逐命令按批准的 plan 落地。

## 7. 非功能约束

- **本地优先**：观测数据全部来自本机（RPC、配置文件、transcript），不上传、无外部服务、无 API key。
- **零 provider 成本**：观测不调用模型、不产生 token 费用。
- **不占模型上下文**：观测视图是浏览器 UI；观测取数不得向会话注入任何消息。
- **只读无副作用**：观测命令不得改变会话状态、配置或 transcript（验收时验证）。
- **耦合面**：新命令只依赖稳定契约（SessionEntry 格式、既有事件类型），不暴露内部类与实现细节；前端不重复实现投影逻辑（若需投影结果，由核心命令提供）。
- **性能**：观测命令按需、低频调用；上下文解剖若 token 精确计数代价高，允许近似并在视图中标注口径。
- **可维护**：观测命令面保持小而正交；每个新命令须在 rpc-commands.md 同步文档。

## 9. 用户故事

### US-1 上下文解剖

- 作为使用 fdecode 的软件工程师，我要查看当前会话的上下文构成与各部分占用，以便 agent 行为异常时定位原因而不是猜测。
- 验收条件：
  - Given 一个已发生压缩的多轮会话，When 打开上下文解剖视图，Then 能看到 system prompt 分节、工具声明、消息历史、压缩摘要的构成与占用，并能指出压缩切掉了哪些内容。
- 对应：FR-1、FR-4

### US-2 装配确认

- 作为软件工程师，我要查看会话的生效配置（逐键优先级与来源文件）和实际加载的扩展/工具/MCP，以便解释"为什么这里 behave 不一样"。
- 验收条件：
  - Given 两个配置不同的工作区，When 并排查看装配视图，Then 能指出行为差异对应的配置键、来源文件与扩展注册项。
- 对应：FR-2、FR-3

### US-3 治理追溯

- 作为软件工程师，我要追溯某次工具调用是否被钩子拦截或改写，以便区分"模型的决策"和"平台/扩展的治理动作"。
- 验收条件：
  - Given 一个存在 tool_call 拦截或改写的会话，When 查看治理审计，Then 能看到该次调用的处置（拦截/改写/放行）与来源扩展。
- 对应：FR-5

### US-4 机制时间线

- 作为软件工程师，我要看到压缩/重试/溢出恢复等机制事件的发生时序与细节，以便理解会话中途发生了什么。
- 验收条件：
  - Given 一个发生过压缩与自动重试的会话，When 打开机制时间线，Then 事件按序可查且与对话流可对照，细节（触发条件、切点、原因）与 transcript 记录一致。
- 对应：FR-4

### US-5 只读安全

- 作为维护者，我要观测命令全部只读且不注入模型上下文，以便观测面不引入新的行为变量或成本。
- 验收条件：
  - Given 任一观测命令，When 在任意会话状态调用，Then 会话状态、配置、transcript 均无变化，且不产生任何 provider 请求。
- 对应：FR-6

## 10. 验收与成功指标

- 验收命令或步骤：在本仓真实会话（faux provider 驱动即可）上验证各视图数据与 transcript/配置文件人工核对一致；观测命令调用前后 transcript 文件逐字节不变；`pnpm run check` 与 fdecode 测试通过。
- 成功指标：对一组预设"行为异常"问题（多轮遗忘、工具行为差异、疑似拦截），使用者用视图定位原因的时间显著少于仅凭原始 transcript 排查，且无需读源码；新命令面保持小而正交（数量与字段由 plan 冻结）。
- 失败判定：视图数据与 transcript/配置不一致（不可信）；观测命令有副作用或触发 provider 请求；命令面失控膨胀；维护成本超出 3~5 人团队承受能力。
