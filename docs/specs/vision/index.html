项目愿景

动态文档。认识变化时更新，不追求一次写对。

本文档是项目宪法：开发决策不能超越它；冲突时先商议是否修改，再实施。

最后更新：2026-11-06

一句话

oh-my-fde（omfde）最终的产品形态是一个企业内部的 FDE（Forward Deployed Engineer，前置交付工程师）平台。以 Pi 为底座，参考 DSH（DeepSeek Harness）的平台化路径，一步一步演化，而不是重写或整体替换。

演化分三条线并行：教程线以文档为主线，平台化线以代码结构为主线，Pi Web UI 线以独立应用为主线。

当前不做的事：为了改而改。核心代码已经由我们维护，但每次核心改动仍然要先证明现有扩展和配置不够。

产品形态

最终形态：企业内部 FDE 平台。 coding agent 是平台的核心能力，但不是最终产品。

平台要解决的不是“让一个人写代码更快”，而是让 FDE 在企业内部稳定地完成：

  • 理解业务需求，并把它转成可运行的方案；
  • 在真实代码库、数据源和企业系统中工作；
  • 复用团队的知识、技能、工具和交付流程；
  • 让权限、审计、评审和交接成为流程的一部分，而不是事后补丁。

平台至少包含四层：

层 当前状态
核心 agent 基于 Pi，已跑通
工作方式 prompt、skills、扩展、MCP，正在形成
团队协作 Web UI 线已交付第一版（M3/M4：访问、工作区、归属、分享、交接、管理员、审计）；平台化线本体待固化
企业集成与治理 Web UI 线已交付初步集成（M5：GitHub、CI、通知、保留策略）；平台化线本体待固化，治理未开始

近期平台化线本体仍只做前两层；后两层已由 Web UI 线（M3–M5）先行供料。后两层等“用好”阶段暴露真实需求后再设计。

首批用户

第一批 FDE 用户是以 Abel 为首的团队，规模 3~5 人。

这意味着当前阶段的优化目标是：

  • 让团队里每个人都能复用同一套工作方式；
  • 优先解决 3~5 人协作中的真实摩擦，而不是大型组织的治理问题；
  • 团队通过 GitHub Issues 记录任务、bug 和阶段目标；新需求由决策者先发起讨论，再同步到 issue；
  • 平台化能力以这个小团队的维护能力为上限，不按平台团队的规模铺开。

三条目标线

目标不是一条线性路径，而是三条并行、节奏不同的线：

线 1：教程线    理解 → 会用 → 用好                      以文档为主线
线 2：平台化线  骨架 → 核心能力 → 协作 → 企业集成 → 治理  以代码结构为主线
线 3：Pi Web UI 可用 → 对齐 DSH → 会话完整 → 团队可用    以独立应用为主线
  • 教程线回答“怎么理解、怎么用、怎么用好”，产物是文档、示例和验证记录。
  • 平台化线回答“代码和组织结构怎么长”，产物是仓库结构、包边界、扩展点和服务。
  • Web UI 线回答“界面和交互怎么交付”，产物是一个独立可运行的 Web 应用。
  • 三条线互相供料：教程线提供真实用法，平台化线固化结构，Web UI 线提供交互入口和真实反馈。
  • 各线不必互相等待，但都不能先搭空架子；每条线的每一步都要有真实需求或可验证结果。

线 1：教程线（以文档为主线）

1. 理解（已完成基础）

  • 读完核心架构：agent loop、session/transcript、projection、provider、扩展、工具、compaction、TUI。
  • 用可运行脚本验证关键假设，而不是只读代码。
  • 产物：docs/explains/ 27 篇笔记 + 3 个验证脚本。

判定标准：能用自己的话解释一次请求从输入到落盘的完整路径，并能指出扩展点在哪。

2. 会用（当前阶段）

  • 用 Pi 完成真实的 FDE 工作，而不是跑测试样例。
  • 掌握日常操作：会话、分支、压缩、扩展、MCP、模型切换、权限边界。
  • 形成自己的使用习惯和配置，而不是照搬默认值。

判定标准：连续用它处理真实任务，遇到问题知道该看哪一层，而不是靠猜。

3. 用好

  • 让它在团队协作、代码审查、长任务、多项目场景下稳定产出。
  • 建立可复用的 prompt、skills、扩展和配置，把个人经验沉淀为团队工作方式。
  • 明确它的边界：哪些事不该交给它，哪些环节必须人审。

判定标准：别人能按文档复现同样的工作流，效果不依赖某个人的临场技巧。

线 2：平台化线（以代码结构为主线）

按“先骨架、后能力、再协作与治理”的顺序推进：

  1. 仓库骨架（已完成第一版）：明确 apps / packages / extensions 的边界，建立最小可运行的平台入口。
  2. 核心能力：把 FDE 高频工作固化为工具、skills、扩展和服务。
  3. 协作层：项目、任务、知识、评审和交接。
  4. 企业集成：代码托管、工单、知识库、CI/CD、部署、身份与权限。
  5. 治理与规模化：多团队、审计、成本、模型路由和升级策略；在首批 3~5 人团队之外再展开。

平台化线的约束：

  • 优先扩展和配置，不轻易改核心。
  • 每层只做已经被教程线验证过的能力，不预先设计。
  • 保持 fork 历史可追溯；不再以持续 rebase 上游为目标。
  • 核心代码可以修改，但必须走 vision → RAD → plan → 验证，不把“能改”当成“应该改”。
  • 原“增强”不再是第四阶段，而是平台化线的总称。

线 3：Pi Web UI（以独立应用为主线）

按“先可用、再对齐、后完整”推进：

  1. 可用界面：在浏览器里新建会话、发送 prompt、流式查看文本/thinking/工具调用、中止。
  2. 对齐 DSH：布局和设计系统与 DSH 一致，样式用 Tailwind 实现，主题与共享控件成形。
  3. 会话完整：会话列表与恢复、模型切换、费用与 token、steering / follow-up。
  4. 团队可用：团队成员能各自用它完成日常工作，而不是只有作者能跑起来。

实际交付以里程碑 M1–M5 落地：M1 可用界面 + DSH 对齐起步、M2 会话完整、M3 团队可用、M4 协作与交接、M5 企业集成（M4/M5 向平台化线协作层/企业集成供料）。M1 之后以功能深度为主，DSH 视觉与设计系统的完整对齐是否单独排期见“未决问题”。

Web UI 线的约束：

  • 独立应用：不依赖 apps/omfde，不作为 omfde 平台的子模块；先能单独启动、单独交付。
  • 底座不变：通过 Pi 已有的 RPC 或 SDK 接缝接入，不为了 Web UI 重写 agent loop、session 或工具系统。
  • 技术栈：遵循“前端技术栈”一节；Web UI 属于应用型界面，使用 TanStack Start。
  • 本地优先，默认只监听回环地址；M3 起支持 3~5 人团队共用（可选 LAN 绑定 + 访问令牌认证），非回环监听必须启用认证。
  • 不做多租户、组织架构与细粒度权限体系；M3/M4 已引入访问令牌登录与管理员/成员两级角色（RAD 判定为边界内、扩大部署与安全边界），但不做 SSO/LDAP/OAuth 与 RBAC；不做云端 IDE，不替代完整文件树与编辑器。
  • 已通过组合式接入成为 omfde 默认界面（见决策记录“Web UI 作为 omfde 平台界面（组合式接入）”），代码保持独立、不合并；是否进一步做代码级并入仍未决。

布局、设计系统与样式实现

层面 对齐内容
布局 三栏 AppFrame：左侧栏（会话/工作区）、中间会话、右侧可停靠面板；侧栏宽度范围、折叠与自动收起行为；窄屏抽屉；窗口 chrome 留白
设计系统 语义 token 分层（静态色阶 → 语义别名 → 组件变量）；light/dark/system 主题；字号与字体角色分离（正文、代码、终端）；圆角、阴影、焦点环、滚动条由主题统一拥有
样式系统 Tailwind CSS 作为统一实现层：--dsw-* 语义 token 映射为 Tailwind theme 或工具类；共享控件先进 primitives 复用，不在功能包里复制；功能组件只消费语义 token 对应的工具类，不写字面色值、不写主题分支；全局样式表由主题层拥有

与 DSH 的关系

DSH 是参考对象，不是替换目标。三条线只借鉴它的组织方式和已验证做法。

借鉴什么

  • 插件与能力接缝的组织方式：Service Definition / Provider / Consumer。
  • session 作为事实来源，以及 “Model-visible ⟺ logged” 不变量。
  • 多端交付：CLI、Web、SDK、自动化协议共用同一套会话和事件。
  • Web 客户端的布局骨架、token 分层和共享控件复用方式。
  • 企业关注点：sandbox、credentials、approval、telemetry、workspace。
  • 测试与发布纪律：快照回放、真实入口验证、构建产物与源码分离。

不照搬什么

  • 379 个包、30 条 workflow、per-file 100% 覆盖这类大规模流程。
  • 用全插件架构重写 Pi；我们保持 Pi 为底座，优先扩展。
  • DSH 的 pre-stable 契约和 breaking changes 节奏。
  • DSH 样式规范中“只用 CSS Modules、禁止 Tailwind”的限制；我们用 Tailwind 实现同一套设计系统。
  • 为对齐视觉而重写 Pi 的会话、工具或 TUI。

前端技术栈

前端开发统一使用一套栈，避免每个应用各起一套：

场景 栈
应用型界面（Pi Web UI、平台控制台等） React + TanStack Start + Tailwind CSS + Vite
内容型站点（文档、博客、官网） React + Astro + Tailwind CSS + Vite
  • 分界按交互形态，不按项目大小：需要长会话、实时状态和复杂交互的用 TanStack Start；以阅读和展示为主的用 Astro。
  • React 是统一组件模型：两种栈都用 React，组件、hooks 和设计 token 可以互相迁移。
  • Tailwind CSS 是统一样式层：设计系统仍由主题层提供 token，Tailwind 负责消费。
  • Vite 是共同构建基础：TanStack Start 和 Astro 都基于 Vite，构建、开发服务器和环境变量约定保持一致。
  • 具体版本在 plan 中锁定，不在本文档中固定。

已确认的系统认识

这些是后续决策的地基，来自代码阅读和实际运行：

  1. transcript 是追加写的 JSONL，历史不原地修改。
  2. 每条消息在 message_end 落盘。
  3. 请求上下文由 session projection 重建，不是直接复用内存数组。
  4. context_edit 是追加式 amend，原始记录保留。
  5. compaction 是检查点，不是删除；systemMessage 快照保证压缩后 prompt 不丢。
  6. tool_call 是所有工具调用的统一接缝，包括 codemode / MCP 的嵌套调用。
  7. 嵌套调用带 parentToolCallId，返回 { block: true } 可以阻止执行。
  8. 扩展能在不改内核的前提下完成拦截、改写和工具编排。

第 6、7、8 条意味着：权限、审计、门禁这类需求，第一选择是扩展，不是改内核。

2026-11-06：目标顺序调整为 理解 → 会用 → 用好 → 增强

原因：读完并验证 Pi 后，确认现有扩展机制已覆盖最初设想的改造点。在尚未用熟之前修改内核，收益不确定，且会失去与上游同步的能力。

影响：暂缓“权限扩展”等实现工作，先进入“会用”阶段。何时进入“增强”，由真实使用中的缺口触发，而不是由计划表触发。

2026-11-06：AGENTS.md 改为 fork 专属规则

原因：上游 AGENTS.md 仍包含 apps/p2、packages/chord、packages/durable 的规则，这些目录在本 fork 中已删除；同时上游规则没有区分“理解/会用”和“增强”阶段。

影响：删除 Chord v2 章节和 p2/durable 相关命令，新增“当前状态”“环境与测试模型”“分支、Git 与上游”“文档”四节；明确当前阶段优先使用配置和扩展，核心改动必须先在本文档记录决定。中文译本 AGENTS.zh-CN.md 同步更新。

2026-11-06：产品形态澄清为企业内部 FDE 平台

原因：此前把目标描述为“个人和团队都能长期使用的 coding agent”，容易把最终产品误解为一个通用编码工具。实际定位是企业内部的 FDE 平台，coding agent 只是平台的核心能力。

影响：一句话和产品形态改为“以 Pi 为底座，先做透 coding agent，再逐步补齐团队协作、企业集成与治理”。近期仍只做核心 agent 和工作方式两层；平台化能力等真实需求出现后再建设。

2026-11-06：演化路径参考 DSH，但在 Pi 上逐步平台化

原因：DSH 展示了平台型 agent harness 的完整形态，但直接替换底座会丢掉已有的 Pi 理解、扩展和上游同步能力；照搬它的规模会超出当前团队承受范围。

影响：一句话和新增的“演化路径”明确为：单兵可用 → 团队可复用 → 平台化外壳 → 企业集成 → 治理与规模化。只借鉴 DSH 的接缝划分、session 不变量、多端交付和测试纪律，不照搬其包数量、流程规模和契约节奏。

2026-11-06：目标拆成教程线与平台化线

原因：原先“理解 → 会用 → 用好 → 增强”是一条线性路径，把“学习与文档”和“平台代码建设”混在一起，容易让平台化被误解为最后才启动，也容易让教程变成代码工作的附属品。

影响：教程线保持“理解 → 会用 → 用好”，以文档为主线；平台化线按“仓库骨架 → 核心能力 → 协作 → 企业集成 → 治理”推进，以代码结构为主线。两条线并行，但平台化每一步都必须由教程线暴露的真实需求触发。原“增强”不再是第四阶段，而是平台化线的总称。

已由 2026-11-06“Pi Web UI 成为第三条目标线”扩展。

2026-11-06：完成第一版 monorepo 骨架

原因：平台化线需要一个可持续的代码落点，避免平台代码散落在 .pi、脚本或 Pi 核心里。

影响：根 workspace 新增 apps/* 和 extensions/*；apps/omfde 作为第一个平台入口，负责启动 Pi 并设置平台环境；extensions/omfde-core 作为第一个扩展骨架。Pi 包继续留在 packages/，不移动，以保持上游 rebase 能力。根脚本新增 pnpm run omfde。

2026-11-06：分支整理

原因：main 原本只是上游镜像，GitHub 默认分支看不到产品代码；omca 是临时工作分支，名称也不再代表项目。

影响：main 成为产品主分支，承载 Pi 包、平台应用和扩展；pages 保留为独立文档分支；删除 omca。上游同步改为在 main 上 rebase upstream/main。

2026-11-06：明确 vision 的宪法地位

原因：开发过程中容易出现“先做，再补文档”或“用实现反推愿景”的漂移。vision 是项目的最高层约定，不能只作为事后说明。

影响：代码、文档和开发决策都不能超出 vision 的目标、边界和阶段；边界内的实现细节不需要改 vision；与 vision 冲突或需要扩大边界的决策，必须先商议是否修改 vision，并把修改写入决策记录后再实施。

2026-11-06：明确首批用户为 Abel 团队（3~5 人）

原因：此前“第一批 FDE 用户是谁”是未决问题，导致平台化设计缺少规模约束。

影响：近期优先服务以 Abel 为首的 3~5 人团队，解决协作与复用中的真实摩擦；大型组织治理、多团队规模化留到后续阶段。

2026-11-06：明确不向上游 Pi 贡献

原因：本项目是企业内部 FDE 平台，上游 Pi 只作为同步来源；向上游贡献会引入上游门槛和额外义务。

影响：upstream 只用于 fetch 和 rebase；不向上游开 PR，也不 push 分支到上游。PR 只保留两种情况：外部贡献者从 fork 提交，以及决策者特批的内部例外。

已由 2026-11-06“切断上游，转为独立维护”取代。

2026-11-06：包管理器迁移到 pnpm

原因：项目需要更好的 monorepo 依赖隔离、workspace 管理和更快的安装；同时与 DSH 的工程实践保持一致。

影响：package.json 固定 packageManager: pnpm@11.15.1；新增 pnpm-workspace.yaml 和 pnpm-lock.yaml；日常命令、pre-commit、test.sh 和文档改用 pnpm；npm 时代的 install-lock 和发布脚本标记为遗留路径。

2026-11-06：切断上游，转为独立维护

原因：项目定位已经是独立的企业内部 FDE 平台；继续以 Pi 上游为同步基线会限制核心改动，且上游规则、节奏和发布方式与本项目不一致。

影响：删除 upstream remote 和 remote-tracking refs，保留 pi-fork-base-20d86c365 与 omfde-cutover 标签。Pi 代码由本项目维护，核心改动不再受 rebase 约束，但仍按 vision → RAD → plan 控制。不再要求持续同步上游。

2026-11-06：pi-web 引入 SQLite 存储元数据

原因：会话归属、Issue 关联、分享和审计已经超出 JSON 文件能舒适承载的范围，后续任务与项目数据还需要事务、索引和查询。继续用多个 JSON 文件会增加一致性和清理成本。

影响：apps/pi-web 使用 Node 内置 node:sqlite，数据库为 ~/.pi-web/pi-web.db；配置继续使用 config.json。第一阶段把 sessions.json、links.json、shares.json 和 audit.jsonl 迁移到表，导入成功后删除旧 JSON；解析失败时保留文件并阻止启动。未来平台数据使用独立的 ~/.omfde/omfde.db，与 pi-web 通过 API 共享，不共享表。引入前先验证 Node 22 的 WAL、并发、迁移和权限。

2026-11-06：Web UI 作为 omfde 平台界面（组合式接入）

原因：Web UI 已具备会话、团队访问、分享、交接和审计能力，继续作为独立应用会让用户在两套入口之间切换；但把 apps/pi-web 整体迁入 apps/omfde 会让界面与平台骨架重新耦合。

影响：apps/omfde 默认启动已构建的 Web UI 服务，保留 --tui 回退；通过 PI_WEB_CONFIG、PI_WEB_CWD 和端口共享配置。apps/pi-web 保持独立目录和独立启动方式，不合并代码。后续任务与交接数据通过平台 API 共享，不在本次接入中实现。

2026-11-06：Pi Web UI 成为第三条目标线

原因：此前把 Web UI 当作平台化线的一步，会把“界面交付”和“平台结构建设”混在一起：Web UI 有独立的交付节奏、独立的技术栈和独立的视觉标准，也需要单独验收。DSH 的 Web 客户端已经验证了布局骨架、token 分层和共享控件复用方式，直接对齐它的布局、设计系统和样式系统，比自建一套视觉语言更快、更一致。

影响：目标线从两条扩展为三条。新增“线 3：Pi Web UI”，以独立应用为主线，按“可用 → 对齐 DSH → 会话完整 → 团队可用”推进。Web UI 作为独立应用开发，不并入 apps/omfde，也不依赖平台代码；布局和设计系统以 DSH 为参考。是否并入 omfde 由平台化线以后单独决定。具体形态（目录位置、RPC 还是 SDK、事件传输方式、会话生命周期）留给 RAD 决定，不在本文档中锁定。

“是否并入 omfde 由平台化线以后单独决定”已由 2026-11-06“Web UI 作为 omfde 平台界面（组合式接入）”取代；线3 序列与四层状态已由 2026-11-06“Web UI 线 M1–M5 落地，正文同步到既成事实”同步。

2026-11-06：Web UI 样式实现使用 Tailwind CSS

原因：维护者不熟悉 CSS Modules，强制沿用 DSH 的实现方式会提高上手和评审成本。DSH 的价值在布局骨架和设计系统，不在“必须用 CSS Modules”这条实现约束。

影响：“布局、设计系统与样式实现”中，样式系统改为 Tailwind CSS：--dsw-* 语义 token 映射为 Tailwind theme 或工具类，功能组件只消费语义 token 对应的工具类。设计系统仍与 DSH 对齐，实现层有意偏离 DSH 的样式规范；这一偏离记录在“不照搬什么”中，避免以后被误认为疏漏。

2026-11-06：前端开发统一技术栈

原因：前端应用和内容站点如果各自选框架，构建、路由、样式和部署方式会分裂，团队需要重复学习和维护。React 是统一的组件模型，Tailwind 是已确定的样式层；TanStack Start 和 Astro 都基于 Vite，分别覆盖应用型与内容型场景。

影响：新增“前端技术栈”一节。应用型界面统一 React + TanStack Start + Tailwind CSS + Vite；内容型站点用 Astro 替换 TanStack Start，即 React + Astro + Tailwind CSS + Vite。Pi Web UI 属于应用型界面。具体版本在 plan 中锁定。

2026-11-06：新增 apps/pi-web 独立应用包

原因：Pi Web UI 需要独立启动、独立交付的代码落点；放进 apps/omfde 会让界面与平台骨架耦合。按 AGENTS 规则，新增 workspace 包需要先在 vision 记录决定。

影响：package graph 新增 apps/pi-web（包名 @omfde/pi-web），不依赖 apps/omfde，也不共享平台代码。需求与实现方案见 docs/rads/pi-web.md 和 docs/plans/pi-web.md。

2026-11-06：Web UI 线 M1–M5 落地，正文同步到既成事实

原因：M1–M5 需求（docs/rads/pi-web*.md）均已由决策者确认、实现并验证（各 plan 切片附 pnpm run check、app 测试与 Playwright 冒烟结果），feat 已提交推送，omfde 组合式接入已完成；但本文档正文的四层状态表、线3 序列与约束仍停留在 M1 之前的表述。

影响：四层状态表的“团队协作/企业集成”更新为“Web UI 线已供料、平台化线本体待固化”；线3 标注 M1–M5 实际推进；约束中“单用户/回环”“不做登录/权限”“是否并入 omfde”同步为 M3 团队共用与令牌登录、M3/M4 两级角色、组合式接入既成事实。本条为正文与已批准决策（各 RAD 确认 + 组合式接入决策）的一致性同步，未新增目标或边界；DSH 视觉/设计系统完整对齐的排期留入“未决问题”。

2026-11-06：新增 apps/docs-site 统一文档站，内容站点落到 Astro/Blume 栈

原因：仓库文档分散在 docs/（项目文档）与 .qoder/repowiki/（Repo Wiki，机器生成）两处，现有 GitHub Pages 站（pages 分支，docsify）内容过时、导航与当前结构不符，且只服务人读。本条落实“前端开发统一技术栈”中“内容型站点用 Astro”的既定决策：用 Blume（Astro + Vite 静态站框架）把两处内容汇聚为一个中文站，人与 coding agent 双读。按 AGENTS 规则，新增 workspace 包先在 vision 记录决定；本条同时回答原未决问题“现有 GitHub Pages 文档站是否迁移到 Astro 栈？”（结论：迁移）。

影响：package graph 新增 apps/docs-site（包名 @omfde/docs-site，private，engines >=22.19），不依赖 apps/omfde/apps/pi-web，只读消费 docs/** 与 .qoder/repowiki/**（构建时镜像进包内 content/，为 gitignore 产物）。纯静态发布到 pages 分支替换 docsify（https://fde-group.github.io/oh-my-fde/，base /oh-my-fde），文档内容全部公开（含本 vision）。面向 agent 的表面（llms.txt、每页 .md 镜像、JSON docs API）随静态构建生成；不开 server 端能力（MCP server / Ask AI），保留日后经 deployment adapter 升级的路径。

维护方式

  • 本文档是项目宪法。代码、文档和开发决策不能越过它的目标、边界和阶段；发现冲突或需要扩大边界时，先商议是否修改本文档，再实施。
  • 本文档随仓库提交。目标或边界变化时，直接改本文档，在“决策记录”里补一条，并与相关改动一起提交，不留在未跟踪或未提交状态。
  • 不把本文档写成实施计划；计划属于具体任务。
  • 本文档只回答两个问题：要去哪，以及现在不做什么。
